### 关键结论

**工程结构**：erp-parent 单体系 5 模块 —— `erp-common`（Result/PageResult/异常/PasswordUtil）、
`erp-system`（SysUser/SysRole/SysDept/SysMenu/SysDictType/SysDictData/SysOperationLog/SysLoginLog
+ MybatisPlusConfig）、`erp-basedata`（仓库/供应商/客户/品牌/物料分类/单位/物料）、
`erp-business`（约 130 实体，采购/销售/零售/库存/结算/报表）、`erp-web`（**全部 37 个 Controller 都在
这一层**，启动类 ErpApplication）。前端 `erp-adminPro`（React+Vite+TS），页面树与接口基本一一对应。

**菜单模型**：`sys_menu` 单表树，`parent_id / code / name / title / menu_type / path / component /
permission / icon / sort / visible / status`。`menu_type` 0=目录 1=菜单 2=按钮。授权链
`sys_user_role → sys_role_menu → sys_menu`。

**⚠️ 最重要发现（后续做权限必须先处理）**：后端**完全没有权限校验**。
grep `@PreAuthorize|@SaCheckPermission|RequiresPermission|hasPermission` 全仓 0 命中；
`erp-web` 只有 `CorsFilter`，**无登录拦截器、无 JWT 解析过滤器**；`AuthController` 只签发 token；
`erp-common` 里 `LoginResult` 有 token 字段但**没有 JwtUtil**（pom 里的 jjwt 未真正用起来）。
⇒ `sys_menu.permission` 目前只驱动前端按钮显隐，任何登录用户可直调任意接口。

**功能覆盖**：对照 xingyun，ERP 约覆盖 60%。已落地 8 域（系统管理/基础数据/采购/销售/零售/库存/
结算/报表）。星云独有、ERP 未做的 6 块：**物流管理、商品中心(SPU+SKU+属性+组合商品)、
流程中心(Warm-Flow)、消息中心、开发管理、便携办公(文件收纳箱/在线Excel)**。

## 第三轮：零售模块三个接口报错（表结构缺失列）

### 1. 根因（一句话）

`RetailConfig` / `RetailOutSheet` / `RetailReturn` 三个实体都 `extends BaseBusinessEntity`，
基类带 `create_time / update_time / create_by / update_by / deleted(@TableLogic)` 五个公共字段，
但 `sql/retail_module*.sql` 建表时**漏加**了部分列 —— MyBatis-Plus 按实体拼 SQL，落库即 500：

- `retail_config` 缺 `create_by` / `update_by` / `deleted`
- `retail_out_sheet` / `retail_return` 缺 `deleted`

**教训：新增业务模块时，实体继承什么基类，建表脚本就必须补齐该基类的全部公共列。**
明细表（`*_detail`）的实体是独立实现 Serializable、不继承基类，所以明细表**不需要**这些列 ——
全库有 20 余张 `*_detail` 表都没有 `deleted` 属正常，排查时别把它们当成问题。

### 2. 全库一致性校验脚本（复用价值高）

`.workbuddy/backup/check_entity_columns.py` —— 解析所有 `entity/*.java` 的 `extends` 与 `@TableName`，
对照 `.workbuddy/backup/all_columns.tsv`（由 `information_schema.columns` 导出）找出缺列的表。
本轮实测：65 个实体里**只有零售这 3 张表**有问题。**以后遇到 Unknown column 报错先跑这个。**

### 3. 修复

`sql/fix_retail_table_columns.sql`（幂等，用 `information_schema` 判断列是否存在再 `PREPARE/EXECUTE`）。
MySQL 8 **不支持** `ADD COLUMN IF NOT EXISTS`，只能走动态 DDL 这一招。

### 4. 顺带修掉的静默失败（比表结构更隐蔽）

## 第四轮：零售模块三个业务缺陷修复（自动审核 / 库存校验 / 成本价污染）

修掉了上面「### 5」列的三条。**无表结构变更，纯代码改动。**

### 1. 自动审核真正生效

- `IRetailConfigService` 注入出库/退货两个 Service，`add()` 保存明细后按配置调 `approve()`。
- `add()` 返回体 `void → Map`（`id/code/status/autoApproved`），Controller 同步改，前端据此提示。
- **关键**：`add()` 自带事务，`approve()` 抛异常会回滚整单（含明细）⇒ 不会出现"单据建了库存没动"。
- 修改（update）**不**触发自动审核：已自动审核的单据 status=1，前端本来也没有编辑入口。

### 2. 库存校验

- 新增 `IProductStockService.checkStockEnough(scId, productId, requireNum)`，报错带仓库名+商品名+数量。
- ⚠️ **必须按商品汇总后再校验** —— 同一次出库中同一商品可能落在多条明细上，
  逐条校验会漏掉累计超出（库存 88、两条明细各要 60，逐条都"合法"，累计 120 才会扣成负数）。
- 退货是入库方向，不校验。

### 3. 成本价污染

- `updateStock` 增加 `updateCost` 参数，三个入口语义固定下来（表见 MEMORY.md「库存变动约定」）。
- 新增 `addStockKeepCost`：入库但不更新成本价，给销售/零售退货这类**按售价回冲**的场景用。
- 出库由 `addStock(outNum.negate())` 改为 `subStock(outNum)`。
- 顺带修 NPE：`stock.getTaxPrice().multiply(...)` 在新建库存且 taxPrice 为 null 时抛空指针。

### 4. 顺带修的健壮性问题

- `sheet.getStatus() != 0` → `Integer.valueOf(0).equals(...)`，避免 status 为 null 时拆箱 NPE。
- `refuse()` 拼拒绝原因前判空，此前 description 为 null 会拼出 `"null [拒绝原因: ...]"`。
- `approve/update/deleteById` 补"单据不存在"报错；审核前校验明细非空。
- 清掉两个 Form 里未使用的 `Modal`、`ExclamationCircleOutlined` 导入（tsc 的 4 个 TS6133）。

### 5. 验证结果（8081 实例，全部通过）

## 第八轮：按模块补权限注解（用户说"好的按模块补权限注解"，已完成并实测）

**成果**：37 个 Controller 注入 **224 个 `@SaCheckPermission`**，覆盖 243 个业务端点。
**权限串全部取自既有 `sys_menu.permission`（63 条），零新增、零数据库变更。**

### 做法（可复现）

1. **先导出两侧清单**：
   - 端点：Python 扫 `erp-web/**/*Controller.java` 的类级 `@RequestMapping` + 方法级
     `@XxxMapping`，正则 `@(Get|Post|Put|Delete|Patch)Mapping(?:\(\s*(?:value\s*=\s*)?"([^"]*)"...)`
     → **必须同时记录"无参数 mapping"**（如 `@PutMapping` 裸用），否则漏掉 update 端点。
   - 权限串：查 `erp-data.sys_menu.permission`（63 条）+ **逐角色导出实际权限**
     （`sys_role→sys_role_menu→sys_menu`），这一步是发现"跨模块下拉会被打断"的关键。
2. **建映射表**（三条规则）：
   1. 主查询 + 全部写操作 → 该菜单权限串；
   2. **跨模块下拉数据源 → 不加**；
   3. 细粒度模块（`system:*`、`basedata:warehouse:*`）按动作精确映射。
3. **脚本批量注入**：定位每个 mapping 注解所在行，在**其上一行**插入注解（保持缩进），
   上一行已是 `@SaCheckPermission` 则跳过；文件缺 import 时插在第一个 `import` 前。
   219 个注解一次成型。

### 映射规则 2 为什么是硬规则（本次最重要的判断）

采购经理(R000002) **没有** `basedata:warehouse:list`，销售经理(R000003) 也没有；
仓库管理员(R000004) **没有** `basedata:supplier:list`。
如果给 `/basedata/{warehouse,supplier}/list` 这种下拉加权限注解，
**采购单表单里"选仓库/选供应商"会直接 403，页面当场崩**。
下拉是"为完成本模块操作必须读它模块数据"，不是越权 → 只要求登录。
