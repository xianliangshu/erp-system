### 编号生成的真实问题（值得单独记）

13 个 `*ServiceImpl` 各写一份**几乎逐字相同**的方法，且每个 Mapper 各配一条
`selectMaxCode()` SQL：

```java
private String generateCode() {
    String prefix = "LS" + LocalDate.now().format(DateTimeFormatter.ofPattern("yyyyMMdd"));
    String maxCode = baseMapper.selectMaxCode();
    int seq = 1;
    if (maxCode != null && maxCode.startsWith(prefix)) {
        seq = Integer.parseInt(maxCode.substring(prefix.length())) + 1;
    }
    return prefix + String.format("%04d", seq);
}
```

三个缺陷：① 13 份重复方法 + 13 条重复 SQL；② **先查再算再插 → 并发必然重号**；
③ 前缀硬编码在 Java，改编号规则要改代码发版。

- 新增 `ICodeGenerateService.generate(ruleCode)`（`erp-common`），
  用 `SELECT ... FOR UPDATE` + `@Transactional` 串行化。
- **删除** 28 个 `*ServiceImpl` 里的 `generateXxxCode()` 与 28 个 Mapper 的
  `selectMaxCode()/selectMaxCodeByPrefix()`（全仓已无残留）。

**两个坑**
1. `current_date` 是 MySQL **保留字**（无括号日期函数）⇒ `SET current_date=?` 语法错误，
   列名改 `seq_date`，实体字段 `seqDate`。
2. 存量数据格式不统一：`base_warehouse` 里有 `WH001`（5 字符）而代码生成的是 `WH000004`（9 字符），
   `CAST(RIGHT(code,6) AS UNSIGNED)` 会报 `Truncated incorrect INTEGER value: 'WH001'`
   ⇒ 改用 `CAST(REGEXP_REPLACE(RIGHT(code,N),'[^0-9]','') AS UNSIGNED)`。
3. 初始化 `seq_date` **不能硬编码成今天**（会导致今天首单跳过 0001），
   改成从现有最大编号里 `SUBSTRING` 反推日期段。

**实测**
- 20 并发创建物料 → `MAT000005`~`MAT000024`，连续唯一、**零重号**（返回顺序打乱 = 行锁串行化的证据）。
- 日切重置：`PURCHASE_ORDER` 的 `seq_date=20261001`，今天创建 → `PO202610030001`，从 0001 重新开始。

- **pass 1** 只校验、不写库，把错误全收集起来（`result.addError(rowNum, ...)`）；
- **pass 2** 只有 `result.isAllSuccess()` 为真才统一写入。

行号 = `数组下标 + 2`（Excel 第 1 行是表头）。文件内重复用 `Set` 占位，
**占位放在全部校验通过之后**（否则一行校验失败会误伤后面同名的行）。

**已落地的三个模块**：物料 / 客户 / 供应商，各 3 个端点
`GET /export`（按当前筛选条件不分页）、`GET /template`、`POST /import`。
- Service 层**不碰 `HttpServletResponse`**，导入收 `InputStream`，导出返回 `List<VO>`，
  由 Controller 调 `ExcelUtils.export` —— 避免把 servlet 依赖灌进 service 接口。
- 分类/计量单位按**名称**匹配 ID；状态接受「启用/禁用」或「1/0」；编号留空交给 `ICodeGenerateService`。

## 环境问题：`env` 被劫持（代价很大，务必记住）

`env -u SERVER__PORT -u SERVER__HOST java -jar ...` 在本机**不会启动任何东西**：
PATH 里的 `env` 解析到 `/c/Users/shu/.local/bin/env`，那是一个「修 PATH 的 sh 脚本」，
**静默吞掉 `-u` 参数后直接退出**（退出码 0、日志 0 字节、端口不监听）。
排查耗时很久才定位。
- 正解 1：bash 内建 `unset SERVER__PORT SERVER__HOST && timeout 1800 java -jar ...`
- 正解 2：绝对路径 `/usr/bin/env -u ... java -jar ...`（GNU coreutils 8.32）

另外记录：会话注入的 `SERVER__PORT` 端口号**每次会话不同**（见过 51731 / 53798），
Spring 宽松绑定会把它当 `server.port` 覆盖 `application.yml`。

**核心方案（A）：SPU 作新增维度层，`base_material` 即 SKU**
- 新增 6 表：`base_spu`、`base_sale_property`、`base_sale_property_item`、

**否决的方案（B）**：完全对齐 xingyun，给 13 张表加 `sku_id` 并改唯一键 —— 收益与成本不成正比。

**设计要点**

## 第十四轮：列表页取数收敛改造（用户选定修法 ①）

**背景**：上一轮定位出「第 2 页点搜索发 2 次请求 + 旧结果可能覆盖新结果」的竞态，用户选择修法 ①

**范围扫描**：`pages/**/*.tsx` 共 63 个含取数逻辑的文件 → 筛出依赖里含 `current` 的

**实际采用的写法**（与最初的预想不同，详见 REFERENCE §11）：
筛选字段**留在 `loadData` 里原样引用 `searchXxx`**，只把 `current` / `size: pageSize` 换成 `...query`；
`useEffect(..., [query])` 成为唯一触发源；搜索/重置只 `setQuery((q:any)=>({...q,current:1}))`。
靠「**effect 在渲染后执行 ⇒ 闭包读到的一定是最新筛选值**」这一点，
用最小改动同时消掉双发与竞态。
⚠️ 不能把 `searchName` 塞进 effect 依赖 —— `Search` 的 `onChange` 直接改它，会退化成逐字符实时搜索。

**批量改造**：`.workbuddy/backup/refactor_list_pages.py`
